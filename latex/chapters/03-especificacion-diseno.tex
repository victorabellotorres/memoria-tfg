\chapter{Alcance y justificación}
\label{chap:alcance}

\section{Objetivo general}

El objetivo general del proyecto es estudiar y comparar modelos de visión por
computador para estimar la masa, las calorías y los macronutrientes de un plato
a partir de imágenes, prestando especial atención al equilibrio entre precisión
y coste computacional.

La pregunta de investigación es la siguiente:

\begin{quote}
¿Qué compromiso entre error nutricional y coste computacional ofrecen distintos
modelos visuales cuando se plantea su ejecución en dispositivos con recursos
limitados?
\end{quote}

La incorporación de profundidad, texto u
otras modalidades queda fuera del núcleo y solo se abordará como
extensión si los objetivos principales ya están cumplidos.

\section{Objetivos específicos}

\begin{enumerate}
  \item Revisar los principales enfoques utilizados para estimar propiedades
  nutricionales desde imágenes.
  \item Preparar un conjunto de datos reproducible y verificar sus particiones
  y etiquetas.
  \item Implementar una línea base sencilla que sirva como referencia mínima.
  \item Entrenar o adaptar una selección limitada de modelos visuales de
  distinta capacidad.
  \item Comparar sus predicciones mediante las mismas particiones y métricas.
  \item Medir el tamaño de los modelos, el tiempo de inferencia y, cuando sea
  posible, el uso de memoria y otros recursos.
  \item Ejecutar y evaluar al menos un modelo seleccionado en el entorno de
  computación en el extremo definido para el proyecto, midiendo el coste de
  inferencia bajo las condiciones documentadas. 
  \item Analizar errores, limitaciones y casos en los que las imágenes no
  proporcionan información suficiente.
\end{enumerate}

\section{Justificación}

\subsection{Modelos visuales de aprendizaje profundo}

Se emplearán arquitecturas de aprendizaje profundo porque la entrada principal
es una imagen y la tarea requiere extraer automáticamente características de
ingredientes, textura, forma, contexto y proporciones visuales, y relacionarlas
con cinco variables continuas. Las redes convolucionales, los transformadores
visuales y las arquitecturas eficientes ofrecen familias con mecanismos de
representación y costes distintos; por ello permiten estudiar el compromiso que
plantea el proyecto. En particular, las familias MobileNet se diseñaron para
reducir el coste de inferencia en hardware móvil, mientras que las CNN y los
transformadores permiten representar distintos grados de capacidad visual
\citep{sandlerMobileNetV2InvertedResiduals2019,howardSearchingMobileNetV32019,qinMobileNetV4UniversalModels2024,bianco2DPredictionNutritional2025}.

No se plantea como enfoque principal una técnica clásica de visión seguida de
aprendizaje automático convencional. Un flujo de ese tipo exigiría diseñar y
seleccionar manualmente descriptores visuales y, probablemente, segmentaciones
o reglas específicas para los platos. Puede ser útil como referencia sencilla
si se define un protocolo que lo haga comparable, pero limita el objetivo de
evaluar representaciones visuales aprendidas de forma automática.

\subsection{Modelo especializado frente a una API de un modelo general}

El proyecto no delegará la estimación en una API de un modelo multimodal de
propósito general, como las ofrecidas por OpenAI o Gemini u otros provedores.
Utilizar un provedor externo de un modelo multimodal no permite controlar ni entrenar el
modelo con las mismas particiones y etiquetas que el resto de candidatos, no permite medir el coste de inferencia,
el coste aumenta al utilizar modelos de gran tamaño y propósito general.

Un modelo especializado permite fijar la arquitectura, los datos, las
configuraciones y la versión de inferencia, y medir de manera repetible su
error, tamaño, memoria y latencia. Al ser modelos especializados con un menor tamaño,
también permite ejecutar la inferencia en un dispositivo limitado, lo que es relevante para
la pregunta de investigación.

\subsection{Ejecución local y en servidor}

La ejecución en el extremo (\emph{edge}) se considera porque puede evitar el
envío de imágenes a un servidor, reducir la dependencia de la conexión y dar
una respuesta con una latencia más predecible una vez el modelo está instalado.
Sus límites son la memoria, la potencia de cálculo, el consumo energético y la
posible necesidad de reducir, cuantizar o seleccionar arquitecturas más
pequeñas. 

La ejecución en servidor permite usar modelos de mayor tamaño y hardware más
potente, y simplifica la actualización centralizada de los modelos. A cambio,
introduce transmisión de imágenes, dependencia de red, latencia variable,
coste operativo y requisitos adicionales de protección de datos. El trabajo no
pretende desplegar ni operar un servicio; comparará el coste de los modelos en
un dispositivo limitado o en un entorno que lo represente y documentará qué
condiciones harían viable cada opción.

\subsection{Diferencia entre entrenamiento e inferencia}

También se distinguirá
entre entrenar localmente y ejecutar la inferencia localmente: el entrenamiento
puede requerir recursos de servidor o aceleradores sin que ello determine dónde
se despliega el modelo resultante.



\section{Resultados previstos}

El proyecto deberá producir los siguientes resultados:

\begin{itemize}
  \item un proceso documentado para preparar los datos;
  \item una línea base y varios modelos comparables;
  \item un protocolo común de evaluación;
  \item tablas y gráficos con los resultados de precisión y eficiencia;
  \item un análisis de los errores y de las limitaciones del estudio;
  \item código reproducible y la memoria del TFG.
\end{itemize}

Un demostrador visual sencillo será opcional. No se considera necesario para
responder a la pregunta de investigación, pero será útil para ilustrar los resultados.

\section{Requisitos funcionales}

\begin{enumerate}
  \item El sistema debe cargar y preparar las imágenes y etiquetas del conjunto
  de datos seleccionado.
  \item Debe generar para cada plato una predicción de masa, calorías, grasas,
  carbohidratos y proteínas.
  \item Debe permitir ejecutar una línea base y los modelos visuales elegidos
  bajo un protocolo común.
  \item Debe calcular y guardar las métricas de cada objetivo nutricional.
  \item Debe conservar las predicciones necesarias para revisar errores y
  comparar experimentos.
\end{enumerate}

\section{Requisitos no funcionales}

\begin{description}
  \item[Reproducibilidad.] Las particiones, configuraciones y métricas deben
  quedar registradas para poder repetir los experimentos.
  \item[Eficiencia.] Los modelos deben evaluarse también por su tamaño y su
  tiempo de inferencia, no solo por el error de predicción.
  \item[Claridad.] El código debe separar la preparación de datos, la definición
  de modelos, el entrenamiento y la evaluación.
  \item[Comparabilidad.] Todos los modelos deben usar, siempre que sea posible,
  las mismas entradas, particiones y métricas.
  \item[Uso responsable.] Las salidas deben presentarse como estimaciones
  experimentales y no como recomendaciones médicas o nutricionales validadas.
\end{description}


\section{Obstáculos y restricciones}

Los principales obstáculos previstos son la disponibilidad de cómputo, el
tamaño del conjunto de imágenes y la dificultad de estimar cantidades a partir
de información visual incompleta. Los resultados también dependerán de la
calidad y representatividad de Nutrition5k o los datasets utilizados, que contiene un contexto de captura
concreto y no representa todas las comidas posibles.
